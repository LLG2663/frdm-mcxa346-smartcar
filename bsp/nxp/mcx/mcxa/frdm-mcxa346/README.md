# FRDM-MCXA346 BSP 说明

本文档介绍 NXP FRDM-MCXA346 开发板的 RT-Thread BSP，包含环境搭建、编译、烧写、调试，以及本项目在配置过程中遇到过的问题与解决办法。

## 简介

| 项目 | 说明 |
| ---- | ---- |
| 板卡 | NXP FRDM-MCXA346 |
| 芯片 | MCXA346VLQ |
| 内核 | Arm Cortex-M33 @ 180 MHz，带 FPU（SFPU）与 DSP 指令 |
| 片内 Flash | 1016 KB（`0x0000_0000` 起） |
| 片内 SRAM | 240 KB（`0x2000_0000` 起）+ 8 KB SRAMX（`0x0400_0000` 起） |
| 调试探针 | 板载 MCU-Link（CMSIS-DAP），另有虚拟串口 |
| 控制台 | LPUART2（设备名 `uart2`），115200 8N1 |

上述存储器容量取自 `board/linker_scripts/MCXA346_flash.ld` 的 `MEMORY` 定义；主频取自
`board/MCUX_Config/board/clock_config.c`，`BOARD_InitBootClocks()` 调用的是
`BOARD_BootClockFROHF180M()`。

### 当前演示功能

这是一个**无线串口遥控小车 + 姿态显示**工程，移植自 TI MSPM0G3507 的 CCS 工程
（`workspace_ccstheia/113`）。六块功能，各自一个线程，互不阻塞：

| 功能 | 源文件 | 硬件 | 说明 |
| ---- | ------ | ---- | ---- |
| RGB LED 三色循环 | `applications/main.c` | 板载 LED | 红 → 绿 → 蓝，每 500 ms 切换；`led` msh 命令可手动控制 |
| SSD1306 OLED 显示 | `applications/oled.c` | 0.96" I2C OLED | 128×64，LPI2C2 / `i2c2`，地址 0x3C；车控屏 + 角度屏两块，`oled screen` 切换 |
| JY901S 姿态解算 | `applications/jy901s.c` | JY901S / JY61P | 11 字节帧解析、校验、yaw 校零与归一，输出 0x53 角度包与 0x52 角速度包；yaw 同时喂给直行辅助（不只喂显示） |
| TB6612 双电机闭环 | `applications/motor.c` | TB6612 + 编码器 | 编码器测速 + 增量式速度 PID，5 kHz PWM，方向带死区滞后 |
| **无线串口遥控** | `applications/bt_car.c` | 无线串口模块 | 115200 8N1 单字节命令，上电锁定，`W/A/S/D` 控制，状态锁存到下一个字节（失联保护默认关，`bt link` 可开），`H` 刹车 |
| **编码器速度上报** | `applications/speed_report.c` | 复用无线串口模块链路 | 每认出一个遥控字节就回一行 `spd <a1> <a2> tgt <t1> <t2>`（实测 + 预期），并收 `#` 开头的命令；周期推送默认**开**（`spd <m1> <m2> duty <d1> <d2> tgt <t1> <t2>`，`#off` 关，且只在解锁后推）；`#head ...` / `#motor ...` 会转发给 `Car_CmdHead()` / `Motor_Cmd()`，让这两组整定旋钮能在电池供电、车真的在跑的条件下拧；只 `write` 不 `open` 设备 |
| **直行辅助（航向保持）** | `applications/car.c` | 用 JY901S 的 yaw | 直行时按 yaw 误差给两轮差速修正，积分项在线配平左右轮的硬件差异（实车左轮明显快、走不了直线）；`head` 命令开关与整定，msh 与无线串口 `#head` 同一入口 |

两块屏的分工与切换见 [功能分析](#功能分析)；接线见 [硬件接线](#硬件接线)。

### 板载 LED 与按键

| 功能 | 引脚 | 说明 |
| ---- | ---- | ---- |
| LED 红 | P3_18 | **低电平点亮** |
| LED 绿 | P3_19 | **低电平点亮** |
| LED 蓝 | P3_21 | **低电平点亮** |
| SW2 按键 | P1_7 | 下降沿触发，需 `PIN_MODE_INPUT_PULLUP` |

引脚编号遵循 `drv_pin.c` 的约定：`GET_PINS(port, pin) == 32 * port + pin`。

### 目录结构说明

本 BSP **没有自己的 `libraries/` 目录**，而是复用上级共享目录：`SConstruct` 先找
`<BSP>/libraries`，找不到则回退到 `../libraries`，即 `bsp/nxp/mcx/mcxa/libraries/`。
所有 `drv_*.c` 外设驱动都在那里，但构建产物仍落在本 BSP 的 `build/libraries/drivers/` 下。

也就是说，`libraries/Kconfig` 与 `libraries/drivers/` 是整个 mcxa 系列（mcxa153/156/346/366）
共享的，改动它们会影响同系列的其他 BSP。

## 硬件接线

整机一共 13 根信号线，**全部落在 Arduino 排针（J1/J2）上**，不用碰 mikroBUS 座、不用飞线、
不用焊未贴装的排针（无线串口模块回程那根在 J2 的模拟侧，不在 D0~D19 编号里，见下）。

| 功能 | MCU 脚 | Arduino | 信号 | 方向 |
| ---- | ------ | ------- | ---- | ---- |
| 控制台 | P2_3 / P2_2 | D0 / D1 | LPUART2（`uart2`），115200 8N1 | 收 / 发 |
| 电机 1 方向 AIN1 | P3_31 | D2 | GPIO | 出 |
| STBY（两路共用） | P3_14 | D3 | GPIO，**高电平使能** TB6612 | 出 |
| 电机 1 方向 AIN2 | P4_7 | D4 | GPIO | 出 |
| 电机 1 编码器 A 相 | P3_1 | D5 | GPIO，上升沿中断 | 入 |
| 电机 2 编码器 A 相 | P3_17 | D6 | GPIO，上升沿中断 | 入 |
| 电机 2 方向 BIN1 | P3_22 | D7 | GPIO | 出 |
| 电机 2 方向 BIN2 | P4_3 | D8 | GPIO | 出 |
| JY901S TX → MCU | P3_13 | D9 | LPUART3\_RXD（ALT3），115200 8N1 | 入 |
| **无线串口模块 TX → MCU** | **P3_11** | **D10** | **LPUART5\_RXD（ALT8），115200 8N1** | **入** |
| **无线串口模块 RX ← MCU** | **P1_10** | **J2-3** | **LPUART5\_TXD（ALT8），115200 8N1** | **出** |
| 电机 1 调速 PWM | P3_8 | D11 | FLEXPWM0\_A1 → 设备 `pwm1`，5 kHz | 出 |
| 电机 2 调速 PWM | P3_10 | D13 | FLEXPWM0\_A2 → 设备 `pwm2`，5 kHz | 出 |
| OLED SDA / SCL | P1_8 / P1_9 | D18 / D19 | LPI2C2（`i2c2`），地址 0x3C | 双向 |

供电与几个必须知道的点：

- **无线串口模块和 JY901S 都是 3.3 V 逻辑，VCC 必须接 3V3。** 供 5 V 会打坏模块，也可能打坏板子的 RX 脚。
- **无线串口模块现在接两根：模块 TX → 板子 D10，板子 J2-3 → 模块 RX。** 去程（`D10`）跑遥控
  命令；回程（`J2-3`）跑编码器速度上报 —— 每认出一个遥控字节就回一行
  `spd <a1> <a2> tgt <t1> <t2>`，上位机连上后发 `4F` 解锁、再按方向键就能看到。
  板子 TX 是 3.3 V，模块 RXD 也是 3.3 V 逻辑，直接接即可，不需要电平转换。
- **回程为什么是 J2 第 3 脚（P1_10）**：LPUART5\_TXD 在这颗芯片上有两个焊盘 —— P3_10 /
  Arduino D13 和 P1_10 / J2 第 3 脚。P3_10 被电机 2 的调速 PWM（FLEXPWM0\_A2）占着，
  而 FLEXPWM0\_A2 **没有第二个焊盘**，换不动，所以走 P1_10。它在整个 BSP 里原本零引用
  （CAN0\_TXD 也复用在 P1_10，但本 BSP 没开 CAN），等于白空着。同一个 LPUART5 一个收一个发，
  TX/RX 是两根独立的线，互不干扰。
- JY901S 的 RX（模块 RX ← 板子 P3_12）是可选的，本工程不向模块发指令，接不接都行。
- **P3_11 与 mikroBUS 的 LPSPI1\_PCS0 共用同一个焊盘**，二选一。`pin_mux.c` 里用
  `#ifdef BSP_USING_UART5` 把这一脚让给了无线串口（本 BSP 的 SPI1 驱动本来也没使能）。
  D10 在排针上，SPI 那一路只有 mikroBUS 座上有，所以实际不冲突。
- **不要对手册里的 P4_4 抱期望**：P4_4 是 LPUART4\_RXD，但它在 **J8** 上，而 FRDM-MCXA346
  的 J8/J19 是 **DNP（未贴装）**——A346 没有 FlexIO 模块，NXP 没焊这两排。这也是
  无线串口模块最终选 P3_11 而不是 P4_4 的原因：P3_11 在 Arduino 排针上，插上就能用。
- TB6612 的 VM 接电池（电机电源），VCC 接 3V3（逻辑电源），两边 GND 与板子共地。
  电机的电源噪声很大，OLED 和 IMU 尽量用板子的 3V3，不要和电机 VM 共用一路。

## 功能分析

### 数据通路

五个独立的输入输出方向，两两之间只通过共享变量交接，没有互相阻塞：

```
无线串口模块 ──LPUART5,115200──> bt_car.c 收字节 + 状态机(线程 prio 23)
   ^                        │  只表达"要往哪走、多快"
   │   spd <a1> <a2>    v
   │   duty <d1> <d2>  car.c 动作层（前进/后退/弧线/自转/刹车）
   │   tgt <t1> <t2>      │  motor_set_target()  只设目标转速
   │   认出一个就回一行    v
   └── speed_report.c ──> motor.c  编码器测速 + 速度 PID + H 桥(线程 prio 21)
        (线程 prio 24)      │  运行期唯一的占空比/方向写入者
        只读 motor_get_speed() v
                            TB6612 ──> 两个直流电机

JY901S ─LPUART3,115200─> jy901s.c 解析(线程 22)
            │
            ├─> angle_display.c 显示线程(prio 26) ──LPI2C2──> SSD1306 128×64
            │            ^                                     ▲
            │            └───────── bt_car.c 的状态/计数 ───────┘
            └─> car.c 直行辅助(线程 prio 21)：直行时按 yaw 给两轮差速修正
                              └──> 同一条 motor_set_target()
```

关键点：**遥控这一层只说"要往哪走、多快"，不碰占空比也不碰 H 桥方向。**
占空比和方向全部由 `motor.c` 的速度 PID 线程去写，它是运行期唯一的执行器。
分层见 `applications/car.h` 头部。

**速度上报（`speed_report.c`）挂在同一条无线串口模块链路上，两个方向各占一根线**：
去程（板子 D10 ← 模块 TX）只由 `bt_car.c` 收，其它模块不得再 `open` / `configure` /
注册 `rx_indicate`（`rx_indicate` 是单回调，抢了遥控就失灵）；回程（板子 J2-3 →
模块 RX）由 `speed_report.c` 独占写入。所以它**只 `find` + `write`，从不 `open`
`uart5`** —— 波特率跟着 `bt_car.c` 的 `BT_BAUD_RATE` 走。细节见 `speed_report.h`。

### 无线串口命令表

串口助手用 HEX 模式发（发的是同一个字节，HEX 和文本模式都不影响协议），115200 8N1：

| 字节 | 字符 | 动作 |
| ---- | ---- | ---- |
| `57` | `W` / `w` | 前进 |
| `53` | `S` / `s` | 后退 |
| `41` | `A` / `a` | 原地左转（逆时针） |
| `44` | `D` / `d` | 原地右转（顺时针） |
| `20` | 空格 | 刹车 |
| `58` | `X` / `x` | 刹车（等效，有些串口助手会吃掉空格） |
| `4F` | `O` / `o` | **解锁** |
| `48` | `H` / `h` | **上锁并刹车** |
| `0D` / `0A` | `\r` / `\n` | 忽略（串口助手自动补的行尾） |

左右以车自身为准（从车顶往下看，逆时针为左），和 JY901S 的 yaw「左转为负」是同一套约定。

**遥控是「切换式」的，不是「按住式」的**：收到一个字节就进那个状态，然后**一直保持**，
直到下一个字节进来（`W` 之后车一直前进，直到你再发 `S` / 空格 / `X` / `A` / `D`）。
所以**长按和点一下的效果完全一样** —— 串口助手按一下只发一个字节，车也会一直跑
（这一点和下面的失联保护相关，默认是关的）。

#### 回程：编码器速度上报（`spd <a1> <a2> tgt <t1> <t2>`）

**收到一个遥控字节就回一行**，行尾 `\r\n`：

```
spd 33 33 tgt 33 -33
```

- 前两个数是电机 1 / 2 的**实测**转速，`tgt` 后面两个是各自的**预期**转速。
  刻度是 **1 个编码器计数 / 50 ms 采样 = 24**
  （`car.h` 的 `CAR_SPEED_PER_COUNT`，和 msh 上 `bt speed` 同一套刻度），
  所以读数只会是 24 的倍数 —— 刚起转时是 24，不是 0。
- **实测只有幅值，方向看 `tgt` 的符号。** 编码器只接了 A 相（`motor.c` 文件头
  「只计 A 相」那一段），计数本身就是非负的；`tgt` 带正负号，负表示该轮被命令反转
  （比如原地转时的其中一轮）。所以「实际跟没跟上预期」直接比这两组数，方向只能
  看 `tgt`。
- **只有认出来的遥控字节才回**（W/S/A/D/空格/X/H/O）。串口助手自动补的 `\r\n` 不算，
  不回 —— **这个口上电后是安静的，不会自己刷屏**，发一个字节才回一行。
- **两次回包至少隔 50 ms**（`SPD_RATE_MIN_MS`）。按住按键或摇杆时字节是连发的，
  每个都回会把 115200 灌满（这一路发送是忙等自旋，一行约 5 ms 的 CPU），
  所以连发时大约每 50 ms 回一行。
- **别想着改成浮点。** `rt_kprintf` 和 `rt_snprintf` 用的都是 tiny vsnprintf，
  两个都不支持 `%f`（会原样打出 `%f`），LFLAGS 里也没有 `-lm`。一个计数就是 24，
  小数位本来也没意义。

#### 回程：周期推送（`spd <a1> <a2> duty <d1> <d2> tgt <t1> <t2>`）

**另有一路周期推送，解锁后自动每 100 ms 一行**，[默认**开**]：

```
spd 17 16 duty 1600 1970 tgt 19 15
```

- 前两个数是两轮**实测**转速（同上，只有幅值）；`duty` 是各自的 PWM 占空比（0~4000）；
  `tgt` 是**真正下发下去的目标** = 上层基准 ± `corr`。刻度都是 1 个计数 = 24。
- **`tgt` 这一段是航向外环唯一的观察窗**。`corr` 是外环的全部输出，而它只体现在 `tgt` 里；
  `tgt` 减去基准（`bt speed`，默认 400）就是 `corr`。上面那条「收到字节就回一行」也带
  `tgt`，但它跟按键节奏绑在一起、每 50 ms 才一条，**车跑起来的整段时间里采不到几行**——
  要看外环在不在使劲、使劲多少，看这一路。
  上面那行读作：目标被外环拉成了 19 / 15（基准 17），**而实测仍差 1 个计数** ——
  外环在压右轮，但两轮还是不一样快，这时该看 `duty`：右边顶到 4000 就是权限不够。
- **`duty` 是判断内环"在调节"还是"顶死了"用的**。插着 USB 时电机供电会从 7.49 V 塌到
  3.56 V，msh 的 `motor status` 量到的根本不是车工作时的读数，所以只能走这一路。
  两轮 `duty` 都在 1000~3000 且随时间小幅变化 = 内环正常；有一路长期 = 4000 = 它在这个
  电压下**够不到**目标转速，调 kp/ki/kd 都没用，先从供电/机械上解决。
- 关掉用 `spd off` / `#off`（再开 `spd on` / `#on`）。开着时也只在【已解锁】的情况下推，
  上电和上锁时链路是安静的。这个开关只管周期推送，不影响上面那条「收到字节就回一行」。
- **一行 41 字节封顶**（`SPD_LINE_MAX` = 48）。这一路发送是忙等自旋，41 字节在 115200 上
  约占 3.5 ms 的 CPU，所以周期下限是 50 ms（`SPD_RATE_MIN_MS`），别往个位数毫秒调。

#### 回程：`#` 开头的命令

上位机上换成**文本模式**发下面这几条，必须以 `#` 开头、以换行（`\r\n` 或 `\n`）结尾：

| 发出去的 | 作用 | 回包 |
| -------- | ---- | ---- |
| `#on` / `#off` | 开 / 关**周期推送**（默认开） | `ok on` / `ok off` |
| `#rate <ms>` | 改推送周期（50 ~ 60000） | `ok rate`，越界回 `err rate` |
| `#status` | 要一份状态 | `sta report=off rate=100 tx=1234 fail=0` |
| `#once` | 立刻发一行（就是周期推送那一行） | 一行 `spd 33 33 duty 1600 1970 tgt 33 33`，再补 `ok once` |
| `#both` | 要一份**实际 + 预期** | **一行**：`spd 33 33 tgt 33 -33`（**不补 `ok`**） |
| `#head ...` | 航向外环的开关 / 增益 / 符号，词和 msh 的 `head` 完全一样 | `ok head` / `err head` |
| `#motor ...` | `motor` 命令整条转发（`ff` / `stop` / `status` / `<1\|2> <v>`） | `ok motor` / `err motor` |
| `#bt ...` | `bt` 命令整条转发（`link` / `status` / …）。**失联急停只能从链路上开**：车跑起来是电池供电、插不了 USB，而它默认是关的 | `ok bt` / `err bt` |
| `#follow ...` | 航点跟随（`begin` / `wp` / `end` / `start` / `stop` / `ping` / …），见「航点跟随」一节 | `ok follow` / `err follow` |

`#head` / `#motor` / `#bt` 是为**整定**开的，见下一节「直行辅助」和「遥控速度的整定」：
这两套旋钮只能"看着车"调，而车必须落地跑、落地就得电池供电，msh 偏偏要插 USB
（一插电机供电就塌）。**只转发这三个名字**（`bt` 也是这个理由：失联急停默认关着，
而"打开它"这个动作只有落地跑的时候才需要做），不是一条通用远程 shell —— `#` 那道闸门
本来就是为了别让命令里的字符被当成遥控命令执行。`#motor stop` 顺带成了无线串口可达的急停。
两个命令的**回包只有一行 `ok` / `err`**：它们真正打印的内容走的是 uart2 控制台，
这条链路上看不见，数值从周期推送那一行里读。

`#both` 那一行的格式与「收到遥控字节就回」的完全一样，也和 `spd both`（msh）推出去
的完全一样：`spd` 后面是 `motor_get_speed()`（实测、无方向），`tgt` 后面是
`motor_get_target()`（预期、**带正负号**）。所以「实际对不对得上预期」直接比这两组数，
方向只能看 `tgt`；上位机上原有的 `spd` 解析不用改。

`#` 后面也可以把 `spd` 写上（`#spd rate 200`、`#spd both`），和 msh 上敲的完全一样，
写不写都认。一条命令回一行（`#status` 和 `#both` 例外：只回数据，不补 `ok`；`#once`
反过来多一行 —— 先 `spd` 数据行，再补 `ok once`）、空行忽略；
一行超过 47 字节或混进不可打印字节时整行作废（丢到行尾为止），不会把半行当命令执行。

**`#` 不能省。** 这条链路同时跑遥控：`bt_car` 把 W/S/A/D/空格/X/H/O 逐字节当运动命令执行，
而 `rate 200` 里就有一个 `a`（原地左转），`spd rate 200` 里更是有 `s`（后退）、`d`（原地右转）
和两个空格（刹车）—— 不加前缀等于边发命令边把车开走。`#` 不在遥控命令集里，拿它当
「这条后面是 speed_report 的、遥控别管」的闸门。它只占一个字节、没有「等第二个字节才能
判断」的中间态，所以**遥控字节不会被延迟**，也不会有卡在半条命令上的状态（收一半就断的
行有 200 ms 超时兜底，超时后整条作废、恢复成普通遥控字节）。

**这条链路上两个模块的分工**（改代码前必读）：去程只由 `bt_car.c` 收，它是 `uart5` 的
持有者；`speed_report.c` 只在需要发数据时 `rt_device_write()`，**从不 `open` / `configure`
设备**。原因是 `rt_serial_open()` 每次都会无条件覆盖 `open_flag`（`dev_serial.c`），
而 `rx_indicate` 是**单回调**，第二个使用者一注册就把遥控的挤掉了。同理，波特率也不在
`speed_report` 里设，它跟着 `bt_car.h` 的 `BT_BAUD_RATE`（115200）走。
字节的交接方式是：`bt_car.c` 读到每个字节后**先**交给 `speed_report_rx_byte()` 认领，
认领走的（`#` 命令）不再进遥控分派 —— 顺序反了就会边解析命令边动车。

### 上电为什么是锁定的

上电默认**上锁**：只回显、绝不动电机。W/A/S/D 在上锁状态下**只计数不执行**，
计数解锁后会显示在屏幕第 4 行，所以「发 W 看到 Ok +1」本身就是一条数据通路自检。

这么做是因为**波特率不对时收到的字节基本是随机值**，而单个随机字节有约 1/128 的概率
正好等于 W/A/S/D——那一刻车会突然窜出去。所以先解锁，再让运动命令生效。

解锁（`4F`）这个动作**本身绝不动车**，只是把闸门打开。就算误码把车解锁了，还得再来
一个恰好是 W/A/S/D 的字节车才会动。真正防「整条链路是垃圾」的是下面的失联保护 ——
但它默认是**关**的（原因见那一节），要用得自己在 msh 上 `bt link 1000` 打开。

**为什么是单字节解锁**：这个工程早期版本用 `47 4F` 两字节序列（先收 `G` 再收 `O`），
废掉了——那个 `arm_seq` 一收到 `G` 就**永久**停在 1（没有任何超时），于是只要之前有过
一个落单的 `47`，之后随便哪个 `4F` 都能解锁，现象就是「有时候发一个就行、有时候又不行」。
单字节版没有残留状态，行为是确定的。

解锁/上锁**不计入**命令计数——它们是状态开关，不是运动命令。

### 失联保护（新增，源工程没有实现；**默认关**）

源工程的 `main.c` 头部注释写着「真正防整条链路是垃圾的是失联保护（一段时间没收到任何
字节就自动刹车）」，但翻遍代码没有任何超时逻辑——`no_data_ms` 只是 IMU 丢帧计时。
**这个功能在源工程里是不存在的。**

本 BSP 补上了，但**默认关掉**（`BT_LINK_TIMEOUT_MS = 0`）：串口助手按一下只发一个字节，
开着的话车跑 1 秒就被自动刹停，现象正是「转一下就停」，和上面说的「切换式遥控」冲突。
默认行为就是**锁存**：进了哪个状态就一直保持，直到下一个字节。

打开之后的行为：解锁状态下，只要车正在动、且超过设定时间没收到过任何字节，就立刻刹车
并回到 `BRAKE`。刹完**保持解锁**——上位机重连后直接按 `W` 就能继续，不用再发一次 `4F`。

```bash
bt link 1000     # 打开：1 秒没字节就刹车
bt link off      # 关掉（默认就是这个）
bt status        # link= 显示当前值，关着时打 link=off
```

> **⚠️ 打开之前必须知道的取舍**：「车正在动」和「上位机还连着但用户没再按键」，在单片机
> 这边看起来完全一样：都是「收到了一个 W，然后没有新字节」。所以超时长度必须和上位机端
> 的发送方式匹配：
>
> | 上位机端手法 | 建议 |
> | ---------- | ---- |
> | 有「定时发送 / 循环发送」 | `bt link 500`，手感最好 |
> | 反复点按 W | `bt link 1000` 基本不会误刹 |
> | **长按 W 不放**（助手只在按下时发一个字节） | **别开**，会刹停 |
>
> 反过来，**关着的时候无线串口掉线/上位机走远，车会一直按最后一个命令跑** —— 这一版按用户
> 要求改成锁存，接受这个风险；试车时把车扶住或架空。它是运行期开关，不用重新编译。

### 遥控走闭环，不是直接给占空比

源工程的 `car.c` 直接写 PWM 占空比，并且在 `Car_Init()` 里把控制模式钉成「角度控制」，
**故意让速度 PID 保持惰性**（源工程的速度环本来就是死代码）。本 BSP 反过来：

| | 源工程 113 | 本 BSP |
| --- | --- | --- |
| 遥控输出 | 占空比（`CAR_DUTY_RUN 1600`） | **目标转速**（`CAR_SPEED_RUN 400`） |
| 谁写 H 桥方向 | `car.c`（带一套预充电/翻转保护） | `motor.c` 的 `motor_update_direction()`，带 `DIR_DEADBAND` 滞后，**换向前先卸力** |
| 谁写占空比 | `car.c` 直接写 | `motor.c` 的 `DC_MOTOR_PID()` |
| 速度 PID | 不生效 | **执行器，每 50 ms 一拍** |

因此源工程 `car.c` 里那套 H 桥换向保护，**「谁写方向」那一半整段删掉了，不是漏掉**：
闭环路径下 `motor_update_direction()` 已经按目标符号带死区换向，两处都写方向就是两个写入者
抢同一个 H 桥。源工程 `car.c` 自己的注释说 car.c 是「运行期唯一的写入者」——那句注释在本 BSP
里由 `motor.c` 的 PID 线程接管了。

**但「先卸力再翻桥」那一半是必需的，已经补回 `motor.c`**（`motor_switch_dir()`）。移植时一度
整段删掉，理由是「`motor_update_direction()` 已经带死区滞后换向」——那个理由站不住：
`DIR_DEADBAND` 只防「目标在 0 附近来回抖」，防不了命令级的符号翻转，因为 `+800 → -800`
是一步到位的（这里 800 只是示意「一个像样的目标值」，与默认档无关），**根本不经过死区**。不清零占空比就翻桥，轮子还在按旧方向转、PWM 还挂在旧占空比上，
桥臂就是反接（电流冲击 + 机械顿挫）。现在这段逻辑是唯一的换向写入点，顺带也修掉了同根因的
另一个现象：刹车后再起步本来是「0 → 上一轮残留的占空比」一步跳变，会窜一下。

**这块的收益**：负载变化（爬地毯、电池电压下降）时轮速不再跟着掉，两轮速度也天然一致，
直行不会跑偏。**代价**：遥控速度的刻度变了，需要台架整定（见下）。

### 遥控速度的整定

遥控速度用的是 `motor.h` 的「目标转速」刻度。这个刻度**已按实车标定过**——
`applications/motor.h` 的 `Encoder`（每转脉冲数）从源工程照搬的 13 改成了实测的 440，
来历注释在那边。标定之后刻度就是近似物理量：

```
speed = counts / 440 * 3.14 * 67 * 50   →   1 个编码器计数 / 50 ms 采样 = 24 个刻度
                                                 1 个刻度 ≈ 0.40 mm/s
```

也就是说转速读数只能取 **0 / 24 / 48 / 72 …** 这些离散值。台阶在默认档（400 ≈ 17 个计数）上
约 6%，内环压得住。**换刻度前那条「1 个计数 = 809、2400 档才 3 个计数、台阶 34%」的粗糙
刻度是标定错误造成的**（分母用了 13 而不是 440，差 34 倍），也正是「车能走直但特别慢」的
根源——旧刻度下写的 2400 在实车上只有约 **2.8 cm/s**，标定修正后 800 是约 **0.32 m/s**
（快了约 11 倍）。README 里凡是提到旧刻度 809 / 2400 / 0.97 m/s 的地方，都是这次修正的对象。

- 默认 `CAR_SPEED_RUN = 400`（≈ 17 个计数 ≈ 0.16 m/s）。标定修正后先按 800 跑了一段，实车
  0.32 m/s 上直行辅助跟不住、走成弧线，所以**折半**换成"慢慢走直"（详见下一节）。上限
  `CAR_SPEED_MAX = 1200`（≈ 50 个计数 ≈ 0.48 m/s）已经**贴着这台车的物理极限**（实测满
  占空比约 0.5 m/s），所以 `bt speed` 的可调范围到 1200 就够了，不用再往上报。
- **别把 `bt speed` 往 200 以下调**：一是 1 个编码器计数 = 24 就是刻度的最小台阶，目标低于它
  没有意义；二是越慢「航向漂移按时间累积」越致命 —— 同一段路要跑更久，累积的转角更多。
  （老版本这里另有一道 12.5%、即满量程 4000 里 500 的**固定占空比地板**挡着，比它更慢的
  目标压不下去。2026-10-13 已换成按目标算的**起步前馈** `motor_ff_duty()`：只在占空比
  正好为 0（刚从刹车/换向起步）的那一拍给一次，不再是一道常驻的地板。它**两路各有一个
  系数**、且必须落地标定，见下面「起步前馈系数」。）

整定步骤：

1. **把车轮架空**（一定要架空，否则车会跑掉）；
2. `motor 1 400` 给一个目标转速，看 `bt status`（或 `motor status`）里的
   实际转速能不能跟上、占空比落在哪；
3. 逐步往上加（`600` / `800` / `1000` / `1200`——1200 就是上限钳位），找到**占空比落在
   30%~60%** 的那个目标转速——这个区间里 PID 还有余量去补偿负载，再高就顶到满占空比
   失去调节能力了；
4. 把选中的值写进 `bt speed <v>` 立即生效，满意后再改回
   `applications/car.h` 的 `CAR_SPEED_RUN` 固化；
5. 落地试车时**先用低速档**（默认档已经是 400；想更慢就 `bt speed 200`），确认左右轮方向对
   （左轮该是 motor1、右轮是 motor2）。若实车**转向和函数名相反**，对调 `car.h` 里的
   `CAR_MOTOR_LEFT` / `CAR_MOTOR_RIGHT` 即可，逻辑代码一行都不用改。**别把这个和"走不直"
   混起来**：转向反了才是对调这两个宏的事，走不直是下一节「直行辅助」的事（硬件偏置，
   对调宏解决不了）。

#### 起步前馈系数（`motor ff`，**落地**标定）

前馈就是"起步那一拍直接把占空比顶到工作点附近"的那一下（`motor.c` 的 `motor_ff_duty()`）。
**两路各有一个系数**，上电默认都是 5.0：

```
起步占空比 = 系数 × |目标转速|，再夹在 500 ~ 3000 之间
```

**为什么必须是两个系数**：两台电机的挣脱点差一大截（架空实测左 680 / 右 1816），而起步
那一拍是**开环**的 —— 前馈给多少就是多少，PID 要到第二拍才开始修。同一个系数意味着给出来
的占空比离两轮各自的挣脱点是**不同的距离**，谁先挣脱谁先转：落地实测起步那一秒左轮最多
领先 **4 个编码器计数（24%）**，车往右画一道弧。**这道弧外环修不了** —— 20 ms 拍的外环
+ 模块 10 Hz 出帧 + 50 ms 的内环，等它看见偏，弧已经画完了。

⚠ **上面那组 680 / 1816 是【架空】量的，落地不能直接用**：轮子悬空只要克服自己的轴承/
减速箱摩擦，落地还要克服静摩擦和车重。同一辆车**落地**实测：占空比已经给到 **2280，
两轮都还没转**（遥控日志里连着两拍 `spd 0 0 duty 2280 ...`）。所以落地挣脱点高一截，
默认的 5.0（目标 400 → 2000）**不够**，起步还要靠 PID 往上爬一两百才真的动 ——
爬的这一两百就是起步滞后的来源，两轮爬得不一样多，就是上面那道弧。

**怎么测**（落地、电池供电、拔掉 USB，命令走无线串口）：

1. **用手按住车**（或者让它顶着墙），发 `W`；
2. 盯周期推送行的 `duty` 两列 —— **`spd` 从 0 跳起来那一拍对应的 duty，就是这一路的
   落地挣脱点**（左列是 motor1 / 左轮，右列是 motor2 / 右轮）；
3. 系数 = 该路挣脱点 × 1.1 ÷ `CAR_SPEED_RUN`（默认档分母就是 400），无线串口上
   `#motor ff 1 <左系数>` / `#motor ff 2 <右系数>` 填进去，**不用重烧**；
4. 验收：起步那 1 秒里 `spd` 两列的差从 4 个计数降到 1 个以内。

- `motor ff`（msh）/ `#motor ff`（无线串口）**不带参数就是看**：它打出两个系数，以及"按当前
  目标会给出多少起步占空比" —— 那个数应当**比实测的挣脱点高一点点**（目标太小、前馈
  根本不会发的那一拍打 `-`）。
- 上限 `MOTOR_FF_DUTY_MAX`(3000) 顺带决定了同一档位上系数最多能调到多大：默认档 400 上
  就是 7.5。**若某一路标定出来顶着上限，说明上限该抬了** —— 它不能压到落地挣脱点以下，
  那样前馈就白给了，起步退回成"靠 PID 慢慢爬"。
- 标定完把值填回 `motor.c` 的 `MOTOR_FF_DUTY_PER_UNIT` 固化（或者就留着运行期设）。
- **改了 `CAR_SPEED_RUN` 之后要重标**："系数 × 目标"是直线近似，只在标定过的那一档附近准。

`CAR_SPEED_MAX = 1200` 是目标值的上限钳位，防止手滑多打一位让 PID 一直顶在满占空比上。
取 1200（≈ 50 个计数 ≈ 0.48 m/s）而不是更小的值，是因为**弧线转弯至少要外侧 2 个计数**
才表达得出来（见 `car.c` 的 `Car_TurnInner()`）。它同时也是 `bt speed` 的可调上限；
**1200 对这台小车已经是满速了，台架上一步一步加，别一上来就跑满档。**

#### 内环增益与刻度（2026-10-13 两轮标定）

默认 `kp 0.5 / ki 0.12 / kd 0.2`，积分限幅 `MOTOR_I_MAX 150`。这组数是**两轮试出来的**，
不是拍脑袋：

**第一轮**：刻度修正那次（`Encoder 13 → 440`）**只改了刻度、没改增益**。同样的物理偏差，
`error` 的数值小了 **809/24 ≈ 33.7 倍**，于是 PID 三项**一起**弱 33.7 倍 —— 内环变软
33.7 倍，起步要 5 秒才爬到工作点（实测左轮 1.4 s / 右轮 5.3 s 才起转，中间 4.2 秒只有
左轮在转，车出去就是一道弧）。

**第二轮（错的方向）**：于是按刻度因子把三个增益乘了 33.7（`2.7 / 0.67 / 1.7`）。**实测把车
打飞了**：

```
W 之后第一拍  duty 0 → 3760     前馈给 2000，PID 又叠了 2.7*400 + 1.7*400 = 1760
W 之后第二拍  顶到 4000
转速          冲到 30 / 27（目标 17 个计数，超调 76%）
占空比        崩到 724，来回摆约 600ms
```

**为什么"按刻度乘"不成立**，两条：

1. **工作点也搬了**。刻度因子只管数字换算，可默认档同时从 2400（= 2.97 个计数）搬到了
   400（= 16.7 个计数），物理速度高了约 5.6 倍。两个因素方向相反，净效果远小于 33.7。
2. **起步那一段被"测量死时间"主导**。前馈把占空比放到工作点之后，电机还没转起来，
   `speed` 读数仍然是 0，这一拍 `error` 就是满的 400 —— `kp` 再大也只是对着一个还没
   更新的数字猛打，**越猛越糟，跟环路刚度无关**。

**第三轮（现在这组）**：让 `kp` 只做微调，起步整个交给前馈。

| 项 | 值 | 为什么 |
| --- | --- | --- |
| `kp` | 0.5 | 起步那一拍 P 项 = `0.5*400 = 200`，只有前馈 2000 的 10%，不会再顶到限幅；稳态下 1 个计数（24 刻度）仍能给出 12 占空比/拍 |
| `ki` | 0.12 | **保持和 kp 的比值约 4**（老的 0.08/0.02 也是 4）—— 这个比值就是积分时间常数（约 4 拍），换刻度不该动它 |
| `kd` | 0.2 | 0→400 的阶跃在微分上贡献 `0.2*400 = 80`，不再是 680。老值 0.05 按比例放大约该是 0.2 |
| `MOTOR_I_MAX` | 150 | 稳态下积分要顶住 `ki*∫ = -kp*e`，即 `∫ = (kp/ki)*e ≈ 4*12 = 50`。等效值 59 太贴边，150 留 3 倍余量，而 `ki*∫` 上限变成 `0.12*150 = 18` 占空比/拍，仍是安全量级 |

- **`motor pid <kp> <ki> <kd>`** 可以在线改（两个电机同时换上，并顺手清掉 `integral` /
  `last_error` / `duty_frac` 这些**按旧增益攒出来的状态** —— 不清的话改完那一拍会被陈旧的
  积分项踢一脚）。改完不用重新编译，当前值随时 `motor status` 看。
- **`motor ff`** 是另一件东西（起步前馈，**两路分开**，而且必须落地标定），不在
  `motor pid` 里，见下面「起步前馈系数」。
- **仍然是起步值**：上台架扫，标准是**起转那一两拍不顶到 4000、转速不冲过目标、稳态不来回
  抽**。

**注意**：遥控速度决定的是「快不快」，走不走得直在下一节。`bt speed` 降档只能把偏置按比例
缩小，**降不掉**。

### 直行辅助（用 JY901S 的 yaw 保持直线）

**问题**：解锁发 `W`，两轮方向都对，但实车左轮明显快（两轮不等速就绕圈，左轮快 = 车往右偏），
走不了直线。

**先排除的不是软件**：`motor.c` 里 motor1 / motor2 两段速度 PID 是**逐行对称**的（同一组
kp/ki/kd、同一套起步前馈和零头进位、积分门限、抗饱和和钳位），编码器初始化和测速公式也一样，
上层没有任何地方给某一轮加偏置。偏置在硬件里——左右电机的摩擦 / 减速箱差异，或者右轮
占空比已经顶到 `MOTOR_PWM_DUTY_MAX` 追不上目标。内环只能在各自的量化台阶内调节，而两个
物理上不同的轮子本来就不会一样快，**靠内环自己配不平**，所以要在它外面再加一层。
（刻度标定修正之后量化台阶从「一个计数 = 34%」降到默认档 400 的约 **6%**，所以"量化误差"
不再是这里的主要理由，主因就是上面的硬件差异。⚠ **但 6% 仍然是 6%**：两轮各差半个计数
就是 6% 的永久偏航，内环看不见 —— 这一条只有外环能跨过去，**增益调多大都修不掉**。）

**办法**：在 `car.c` 里加一层**航向外环**（`Car_StraightTick()`，20 ms 一拍），用 JY901S 的
yaw 给两轮差速修正：

```
err  = 参考航向 - 当前 yaw        （左转为负、右转为正，和模块的约定一致）
corr = kp·err + ki·∫err dt - kd·wz（wz = 模块的 Gz，°/s，同一套符号）
左轮目标 = 基准 + corr，右轮目标 = 基准 - corr     （corr 为正 = 左轮加快、往右修正）
```

- **只有「两轮同向同速」的直行动作参与**：原地自转 / 弧线（`base_l != base_r`）和刹停后
  （`base == 0`）自动退出，`bt_car.c` 一行都不用改。
- **起跑那一拍锁定参考航向**：车现在指哪，"直行"就是哪个方向。重新按一次 `W` 会重新锁。
- **积分项就是自动配平**：它自己收敛到「抵消左右轮差异所需的那一点点差速」然后保持不动。
  只用 P 的话，稳态必须留一个恒定的航向误差去产生那个恒定差速——车是走直线了，但方向是
  歪的、和起跑时指的方向差一截；加上积分项误差才归零。**所以它替代了「手工标定左右轮
  trim」那套**：电池电压、地面摩擦、载荷变了它都跟得上。
- **刹车优先**：外环每拍先核对电机当前目标是不是自己上一拍写下去的值，不是就立刻放弃这一轮
  并且**不下发**。遥控的空格 / `X` / `H`、`Car_Brake()`、msh 的 `motor stop` 都走这条——
  刹车必须刹得住，不会被外环在 20 ms 后顶回来。
- **修正权限给够，但别越界**：`corr` 上限 = 基准速度的 `CAR_HEAD_CORR_PCT`%（默认 100%，即最多
  把慢的那一轮压到停车）。外环唯一的手段是"把快的那一轮压慢"，压到它和慢的那一轮实际转速
  一样为止；只给 ±1 个计数根本不够——外环会顶在限幅上，车照样跑偏（上一版就是这个毛病，
  实车表现正是"左轮飞快、右轮完全跟不上"）。但给一个固定的大数也不行：`corr` 与目标转速同
  刻度（1 个编码器计数 / 50ms = 24），而默认档只有 400，固定上限在低档就成了"比基准还大"，
  而 `Car_Apply()` 下发的是 `base ± corr`——`corr > base` 会把慢的那一轮推成**反转**，
  直行辅助就变成原地打转了。按百分比给，上限跟着档位一起缩放。
- **积分带抗饱和**：积分项长期保持一个非零值是它的本职（在线配平左右轮差异），但若不管它，
  台架上车不动、航向误差永远存在，积分几秒就能攒到限幅，一松手就是满舵（实测现象：手把车
  掰偏一点，两轮猛地一正一反）。现在输出顶到限幅时会把**这一拍新加的**积分退回去，所以被人
  按住、堵转都不会积；同时 `ki` 的默认值从 30 降到了 6（30 让积分项自己几秒就能顶满整个
  `corr` 上限）。
- **陀螺阻尼（`kd`）的量级是算得出来的**：`corr` 以「目标转速刻度」下发（1 刻度 ≈ 0.40 mm/s），
  两轮速差 `Δv = 0.80·corr` mm/s；轮距代码里没有，实车约 130 mm，于是
  `ω[°/s] = Δv/L·180/π = 0.353·corr`。阻尼环的回路增益就是 `0.353·kd`，稳态残余速率
  = `ω_d / (1 + 0.353·kd)`：

  | `kd` | 回路增益 | 漂移抑制 | 1.5°/s 漂移剩 |
  | --- | --- | --- | --- |
  | 1 | 0.35 | 26% | 1.11 °/s |
  | 3 | 1.06 | 51% | 0.73 °/s |
  | **5（默认）** | 2.12 | 68% | 0.48 °/s |
  | 10 | 3.53 | 78% | 0.33 °/s |

  **但 `kd` 到 5 就封顶了**：wz 通路有约 0.28s 的一阶 IIR（`jy901s.c` 的 `KALMAN_K=0.3`，
  模块 10 Hz 出帧）+ 最坏 0.1s 零阶保持 + 内环（50ms 周期）约 0.15~0.3s 响应，合计约
  0.3~0.5s 滞后。按 PM=45° 解，硬顶是 8~10；5 还有约 88° 余量（可用），10 只剩 46°
  （临界，实车会来回摆）。⚠ **增益和相位余量是同一笔钱**——"把 `kd` 调大就能更直"是错的。
  想再往上，得先剪短滞后（内环提速、或把模块出帧率提上去），不是拧这个数。
- **`kd` 对 DC 没有贡献**：它只给相位。把常值扰动造成的**稳态速率**压到零的是 `kp`（靠对象
  自带的那个积分器），把残余**航向偏置**消掉的是 `ki`。所以别指望单独调 `kd` 把弧线调直 ——
  它的价值是让 `kp`/`ki` 能取高而不振，不是替代它们。

| 命令 | 作用 |
| ---- | ---- |
| `head` | 看状态：开关 / 是否在修正 / kp ki kd / 符号 / `base` / yaw / 参考航向 / corr / 积分 / IMU 帧数 / 两轮**实测**转速 |
| `head on` / `head off` | 开 / 关（**当前上电默认开**，`car.h` 的 `CAR_HEAD_ASSIST_EN`；曾经关过、又为什么开回来见本节末尾） |
| `head kp <v>` / `ki <v>` / `kd <v>` | 在线改增益，不用重新编译（`ki` 收在 1~100，`kd` 收在 0~100） |
| `head sign <1\|-1>` | 翻转修正方向（实测"越修越偏"时用；会顺手把积分清零） |
| `head zero` | 把当前朝向记为参考航向（车摆歪了、想重新定"直行方向"） |

**这张表里的命令在无线串口上一样能用**，前面加 `#` 就行（`#head ki 1`、`#head sign -1`），
回包只有一行 `ok` / `err`。这不是顺手加的便利 —— **落地整定只能用无线串口**：这套增益要
"看着车"调，车要跑就得落地、落地就得电池供电，而 msh 一插 USB 电机供电就塌（7.49 V →
3.56 V），调出来的参数不是车工作时的参数。

**上电前必须先做的两步**（都架空）：

1. **符号自检**（最关键的一条：符号反了外环就是正反馈，车会原地打转）。

   先 `head`（或 `#status` 之后插 USB 看）确认 `imu frames` 在涨 —— **`frames=0` 时
   `Car_StraightTick()` 第 3 步直接返回，外环压根没介入**，下面这些现象一个都不会出现，
   别把它当成"符号是对的"。然后发 `W` 让轮子转起来，再**用手把车体往左拧、保持住**：

   | 拧住车头往左时看到 | 结论 |
   | --- | --- |
   | **左轮明显比右轮快**（左轮在把车"往右拽"，对抗你拧的方向） | 符号正确 ✅ |
   | 右轮更快（越拧越猛） | 符号反了 ❌ —— 敲 `head sign -1`（会顺手清积分），再拧一次确认 |

   ⚠ **判据必须是「物理上哪只轮子真的转得快」**，看 `spd` 的**前两列**（编码器实测）
   或者干脆看轮子。**不能拿 `corr` / `tgt` 当判据** —— 它们就是符号算出来的结果，
   拿它们判符号是循环论证：`sign` 一改成 -1，`tgt` 立刻跟着反，看起来永远"对"。
   为什么"左轮快 = 车往右转"：左轮线速度大，车头就往右偏，这正是本节的出发点。

   架空这一条只能证明**外环活着、差速方向对**（轮子悬空时它除了转向没别的表现）。
   真正的判据在地上：**开了之后车变直，不是变得更弯**。

   确认之后把 `car.h` 的 `CAR_HEAD_SIGN` 改成 `-1.0f` 固化（不改也能跑，只是每次上电
   要重敲一遍）。
   ⚠ **别去改 `jy901s.c` 的 `JY61P_YAW_SIGN`** —— 那会连带改掉显示和模块自己的符号约定。
2. **刹车自检**：跑起来之后，遥控的空格 / `X` 和 msh 的 `motor stop` —— 轮子必须**停住不再转**。

**整定**（先架空，确认符号之后再落地）。**下面每一步都在落地、电池供电、拔掉 USB 的
状态下做**，命令走无线串口（`#head ki 1`），`corr` 从周期推送行的 `tgt` 里读：
`corr = tgt − 基准`（基准 = `bt speed`，默认 400 —— 也就是 tgt 显示 19/15 时 corr ≈ +2 个计数）。

1. 先让 `ki = 1`（等于不要自动配平）感受一下：`head ki 1`（无线串口 `#head ki 1`），落地慢速
   直行，会有个稳态航向偏差但**轨迹是直线**；偏差的**大小**由 `kp` 决定，`kp` 大了会
   来回画龙（超调）。
2. 把 `ki` 加回来（从默认的 6 起步，逐步加）：稳态偏差应该慢慢消失，车头指回原方向。
   加太多会在 1~2 秒的尺度上慢慢来回摆（积分振荡），退回一档。
3. **`kd` 别从 0 起扫**：默认 5 就是按上面那张回路增益表算出来的。要扫就 `#head kd 3` →
   `5` → `8` 在**同一条路**上比：车走直了、`tgt` 两列差得少而稳 = 这一档够了；车开始
   周期性来回摆 = **过头了**（相位余量被吃光），退回上一档。`kd` 用的是模块的 Gz，
   噪声比差分 yaw 小，但它的通路（10 Hz 出帧 + 0.28s 一阶 IIR）滞后**最大**，这正是它
   不能往上加的原因。
4. **看 `tgt` 顶没顶上限**：`tgt` 的两列差长期贴着 ±基准（`CAR_HEAD_CORR_PCT` = 100%）
   就是 corr 顶死在限幅上，说明这台车在这一档本来就有一轮跟不上 —— 该降 `CAR_SPEED_RUN`，
   不是继续放大限幅（`Car_Apply()` 下发 `base ± corr`，corr > base 会把慢的那一轮推成反转）。
5. 满意后把三个值填回 `applications/car.h` 的 `CAR_HEAD_KP` / `KI` / `KD` 固化。

**必须承认的限制**（不粉饰）：

- **信息率不是 20 ms**。代码不给模块发配置帧（模块 RX 那根线是可选的、没接），所以外环拿到的
  yaw 由模块出厂设置决定（一般 **10 Hz**）。20 ms 只是"重算"频率，不是新信息频率；想提高到
  100 Hz 得先把模块的 RX 线接上。高频抖动靠内环 + `kd` 压。
- **修正权限的代价，不是"上限"**：`corr` 上限是基准速度的 `CAR_HEAD_CORR_PCT`%，外环因此有权
  把快的那一轮一直压到 0 —— 它总能把两轮拉到等速，**但代价是整车速度被慢的那一轮限制住**。
  `head` 里看到 `corr` 长期顶在 `±corr_max` 上，说明这台车在当前这一档本来就有一轮跟不上，
  这时该**把 `CAR_SPEED_RUN` 降一档**让两轮都回到可调区，车速和直线度都会更好。
- **yaw 会漂**：JY901S 的 yaw 由模块内部融合得到，长时间缓慢漂移。本辅助只做"这一次直行"的
  短时保持，重新按一次 `W` 就会重新锁航向；不做航点、不做里程。
- **装法**：模块必须**水平、刚性**固定在车体上（不能装在会晃的地方）。模块没接 / 没出帧时，
  外环自动不介入（`head` 里 `imu frames=0`），车回到纯差速开环——不会因为 IMU 缺失而失控。

#### 上电默认开；曾经关过，为什么又开回来

`CAR_HEAD_ASSIST_EN` 是 **1**（开）。

**曾经关它的理由，已经作废。** 原先写的是：**「两轮占空比早就双双顶死 4000，外环算出的
差速下发之后两个目标仍在饱和区 —— 差速零执行力，积分于是单调涨到限幅且不回头」**。

⚠ **那个读数是插着 USB 量出来的**，而 USB 一插电机供电就从 7.49V 塌到 3.56V（见「供电与
调试」一节），那种状态下占空比当然会顶死。**同一台车、电池供电**、目标 400 时新的 `duty`
遥测读到的是 **1680 / 2038**，离 4000 很远 —— 差速是有执行力的。

**开回来的实测依据**：电池供电、拔掉 USB、走无线串口跑出来的周期推送里，稳态两轮速度是
**16.86 / 16.50 个编码器计数**（差 +0.36，即 2.1%），右轮要多花约 **408** 的占空比才跟得上
左轮。换算成航向就是 `0.36 × 9.6 mm/s ÷ 130 mm × 57.3 ≈ 1.5°/s` 的漂移 —— 按 0.16 m/s
走 3 米要 19 秒，转角约 29°，横向偏出约 **0.7 米**。这就是"走成弧"的全部来源。同一组数也
解释了为什么内环修不了：**0.36 个计数远小于内环 1 个计数的量化台阶**，它根本看不见这个差。

⚠ **开之前先做符号自检**（本节上面「上电前必须先做的两步」第 1 条）。外环的负反馈依赖
`wz` 和 `yaw` 同向；若模块这两个量符号相反，`P` 是负反馈而 `kd` 会变成**正反馈** ——
一开阻尼就振荡发散。这是"加了阻尼反而更糟"的头号成因。

### 航点跟随（上位机画轨迹，车自己走）

在 PC 上画一条轨迹 → 下发航点 → 车分段走完。**车上没有位置传感器**，这一节的所有
设计取舍都是这一条推出来的，先看它：

- 编码器只接了 **A 相**，所以 `counter_1_A/B` 只有幅值、没有方向；能直接量到方向的是
  **IMU 的 yaw**。也就是说车上唯一的绝对量是航向，"位置"是靠 **航向 + 编码器累计里程**
  推算出来的，会**累积误差**（打滑、轮径误差、航向漂移都会算进去）。
- 因此默认是**分段停走**：每走完一段就刹停，原地把航向重新对到下一段的方位，再走。
  每一段都是一次"重新对准"，累积误差不跨段传递。代价是走走停停、慢。
- `#follow start cont` 是**连续模式**：到点不停、直接转头走下一段，快但误差会连着攒。
  只在轨迹平缓（每段转角很小）时用。

**协议**（走无线串口那条链路，`#` 开头、`\r`/`\n` 结尾、行 ≤ 48 字节，和 `#spd` 那套同一条通路）：

```
#follow begin <n>                    -> ok follow      n 个点，2 ~ 128
#follow wp <x_mm> <y_mm> <h_ddeg>    -> ok follow      一个一个来，逐条 ack
#follow end                          -> ok follow      校验点数后推一行 fol load
#follow start [stop|cont]            -> ok follow      开始；stop=分段停走(默认)
#follow stop                         -> ok follow      立刻刹停
#follow ping                         -> 不应答         纯心跳，见下面「失联急停」
#follow status / odom                -> ok follow + 一行状态 / 里程
#follow sign|tol|kp|lead|spd|margin|vmin|vmax <值>      台架整定，运行期可改
```

**遥测**（车 → PC，跑动时 200ms 一行、空闲 2s 一行）：

```
fol st=<idle|load|turn|settle|drive|done|abort> leg=<i>/<n> d=<mm> yaw=<ddeg> err=<ddeg> ab=<code>
fol load n=<点数> seg=<段数> mm=<总长>
fol odo l=<计数> r=<计数> mm=<里程>
```

单位全是整数（毫米 / 0.1 度）—— 这套 tiny vsnprintf **不支持 `%f`**，见 `speed_report.h`。

**站内坐标**：`x/y` 是毫米、`h_ddeg` 是该点指向下一点的方位角（0.1 度、逆时针为正）。
车上只用**相对角差**：起点那一拍的 yaw 就是第一个点的方位，所以上位机有没有把首段
旋转到 +X 都无所谓，两边自动对齐。

**`ab` 中止码**：1=遥控打断 2=链路失联 3=IMU 无帧 4=航向偏差超限（>45° 持续 400ms）
5=堵转 6=未解锁 7=参数非法 8=单段超时。

**安全性**：`start` 时必须是解锁状态；跑动中任何一个遥控字节（W/A/S/D/空格/H）都会
立刻打断跟随并刹车（`ab=1`），H 上锁同理。航向偏差超过 45° 就放弃 —— 这个阈值必须
**小于** `CAR_HEAD_RELATCH_DEG`(90°)，否则外环会自己偷偷重锁基准，把"走偏了"藏起来。

⚠ **失联急停和跟随是有冲突的，必须一起设**：链路的"失联"判据是"多久没收到字节"，
而 `bt link` **默认是关的**（`BT_LINK_TIMEOUT_MS 0`）。跑动期间上位机要**每 500ms
发一次 `#follow ping`**（固件侧是空操作，只为刷新接收计时），同时用 `#bt link 1000`
把急停打开。桥（`bridge.py`）连上串口时会自动下发 `bt link`，并一直发心跳。
另外 `bt_is_moving()` 只看遥控状态机，跟随运动对它是不可见的 —— `bt_tick()` 里已经
把 `Follow_IsRunning()` 也算作"在动"，否则跟随期间失联不会刹车。

**为什么用 `Car_DriveHeading()` 而不是另写一个航向环**：`Car_StraightTick()` 已经是一个
调好的 20ms 航向外环（带积分抗饱和、带 90° 重锁保护），`Car_DriveHeading()` 只负责
把基准角换成当前段的方位并把积分清零，修正本身还是走原来那一套。跟随状态机就挂在
`car_head_thread` 的循环里（`Follow_Tick()` → `Car_StraightTick()`），**同一个线程顺序调用**，
没有新线程、没有新栈、没有竞态。

**上位机**：页面上画轨迹、采样、可行驶性校验那一套是单文件的 `smartcar-host.html`
（在仓库根目录的 [`host/`](../../../../../host/) 下）。它通过同目录的 `bridge.py`
（本机 Python 服务）下发 —— 页面用 `file://` 打开时浏览器不给 `navigator.serial`，
所以串口只能由那个服务拿着，页面走 HTTP。点数和坐标范围的拦截在两边都做了一遍
（页面提示"把采样间距调大"，桥回绝并带可读原因）。在线演示（页面内置模拟车，
不接真车）：<https://smartcar-frdm-mcxa346.surge.sh/>

### 两块屏幕

| | 车控屏（默认） | 角度屏 |
| --- | --- | --- |
| 第 1 行 | `Yaw  <值>`（IMU 丢了打 `Yaw!`） | `Yaw   <值>` |
| 第 2 行 | `St   <状态>`：DISARM / BRAKE / FORWARD / BACKWARD / SPIN-L / SPIN-R | `Pitch <值>` |
| 第 3 行 | `Rx   <hex> <字符>`：最后收到的原始字节 | `Roll  <值>` |
| 第 4 行 | 上锁时 `send 4F`；解锁后 `Ok <计数>` | `Wz    <值>`（°/s） |

用 `oled screen car` / `oled screen angle` 切换。两块屏共用一个显示线程、一份显存——
OLED 是独占资源，两个写入者迟早会在 `OLED_Refresh()` 的 1024 次 I2C 事务中间被打断，
画出半新半旧的混合屏。

**重画策略**：屏幕内容变了才刷（每块屏各自比一次快照），外加 1 秒一次的心跳兜底。

**上电那张命令表**（`UART HEX 115200` / `W57 S53 A41 D44` / `20 stop  4F=arm` / `H48=disarm`，
照搬源工程的 `ShowBootScreen()`）**实际只显示几毫秒**，等于看不到：显示线程的第一轮就会因为
「屏幕编号变了」清屏重画，而主线程优先级 10、显示线程 26，`main()` 一进开机灯语的 600ms 延时，
显示线程就抢到 CPU 了。没有为它加停留窗口——这张表的信息在下面的「无线串口命令表」和车控屏
第 4 行的 `send 4F` 里都有（见「已知问题」）。

源工程有一条硬约束：`OLED_Refresh()` 阻塞约 300 ms，所以**车在动的期间一次 OLED 都不刷**。
这条约束在 RT-Thread 下不成立——显示在自己的线程里，刷屏不挡遥控线程。所以本 BSP 没有
照搬，顺带修掉了源工程一个真实的表现问题：源工程「车动期间零刷新」意味着
**FORWARD / SPIN-L / SPIN-R 这三个状态名从来没有在屏幕上出现过**（刷屏写在读命令之前，
而车一动就不再刷屏了）。这里状态一变就刷，按 W 屏幕立刻显示 FORWARD。

### 波特率自检

1. 上位机连上无线串口模块，打开任意串口助手（**115200** 8N1）；
2. 随便发一个字符，看车控屏第 3 行 `Rx`：

   | 显示 | 含义 |
   | ---- | ---- |
   | `Rx  57 W` | 收到 0x57 = 'W'，**波特率对** |
   | 乱码或别的值 | 波特率不对（本车配置是 **115200**，见 `bt_car.h` 的 `BT_BAUD_RATE`；模块出厂常见 9600，不能照抄） |
   | 一直 `Rx  -- -` | 根本没收到，查无线串口模块的 TX 有没有接到 D10 |

   自检时屏幕**同时**显示 hex 值和它对应的可见字符，两者互相对应，比纯文本模式更容易
   看出波特率对不对。要更细的观察用 `bt echo on`，收到的每个字节都会打到 msh。

   **乱码时怎么把真实波特率试出来**：把助手当"未知波特率的接收端"，固定发一组
   已知字节（如 `41 42 43`），把助手波特率依次切到 9600 / 19200 / 38400 /
   57600 / 115200，**哪一档能原样显示就是哪一档**（本车是 115200）。
   错配读数是**错位采样**出来的，稳定、可复现，不是噪声。找不到哪档干净、
   或读数随机跳，才是接线 / 电平问题。

3. 发 `4F` 解锁：第 2 行 DISARM → BRAKE，第 4 行从 `send 4F` 变成 `Ok 计数`；
4. 发 `57`：第 2 行变 FORWARD，轮子开始转 —— 而且**会一直转下去**（状态锁存），
   要停就发空格 / `X`（刹车）、发 `48`（上锁刹车），或按板子上的复位。
5. **顺手就能验回程**：每发一个认出来的遥控字节（`4F`、`57`…），助手那边会多一行
   `spd <a1> <a2> tgt <t1> <t2>`。收到就说明回程那根线（J2-3 → 模块 RXD）也是通的；
   收不到就查那根线，**不要去怀疑遥控** —— 去程和回程是两根独立的线。

屏幕一次只看得到 4 行，接上串口在 msh 里敲 `bt status` 能一次看全（解锁态、状态机、
最后字节、计数、失联次数，以及两轮的目标转速 / 实际转速 / 占空比）。

### msh 命令速查

下表全部走串口控制台（uart2，要插 USB）。其中 `head ...`、`motor ...`、`bt ...`、
`follow ...` 四组**同时在无线串口上可达**，写成 `#head ...` / `#motor ...` 就行：这些数
只能在**电池供电、车真的在跑**的条件下拧，而 msh 偏偏要插 USB，一插 USB 电机电源 VADJ
就从 7.49V 塌到 3.56V。无线串口那条链路只回一行 `ok/err <命令名>`，要看数值请读周期
推送行（`spd ... duty ... tgt ...`）或 `fol ...` 那一行。

| 命令 | 作用 |
| ---- | ---- |
| `bt status` | 解锁态 / 状态机 / 失联超时（关着时 `link=off`）/ 最后字节 / 计数 + 两轮目标、实际转速、占空比 |
| `bt speed <v>` | 在线改遥控目标转速，0 ~ 1200（**默认 400**；整定用，不用重新编译） |
| `bt unlock` / `bt lock` | 等同发 `4F` / `48`，不用上位机也能验证状态机 |
| `bt link <ms>` / `bt link off` | 打开 / 关掉失联保护（**默认是关的** —— 车按最后一个命令一直跑） |
| `bt echo on` / `off` | 收到的每个字节都打到 msh（替代屏幕做波特率自检） |
| `head` | 直行辅助状态：开关 / 是否在修正 / kp ki kd / 符号 / `base` / yaw / 参考航向 / corr / 积分 / IMU 帧数 / 两轮实测转速 |
| `head on` / `head off` | 开 / 关直行辅助（**当前上电默认开**，`car.h` 的 `CAR_HEAD_ASSIST_EN`） |
| `head kp <v>` / `ki <v>` / `kd <v>` | 在线改航向外环增益（整定用，不用重新编译；`ki` 收在 1~100，`kd` 收在 0~100） |
| `head sign <1\|-1>` | 翻转修正方向（实测"越修越偏"时用，不用重新编译；会顺手清积分） |
| `head zero` | 把当前朝向记为参考航向（重新定"直行方向"） |
| `spd status` | 周期推送开关 / 周期 / 写失败计数 / 最近一行原文 + 两轮目标、实际转速、占空比 |
| `spd on` / `spd off` | 开 / 关**周期推送**（默认开，等同无线串口上发 `#on` / `#off`） |
| `spd rate <ms>` | 改推送周期，50 ~ 60000 |
| `spd once` | 立刻发一行（**与周期推送同一格式**：`spd <m1> <m2> duty <d1> <d2> tgt <t1> <t2>`，不受开关影响） |
| `spd both` | 立刻推一行**实测 + 预期**（等同无线串口上发 `#both`，控制台也打一份数值） |
| `motor <1\|2> <speed>` | 直接给某个电机一个目标转速（闭环单独验证） |
| `motor ff` | 打印两轮的**起步前馈系数**和当前目标下它会给出的占空比（目标 ≤10 时占空比打 `-`，因为那时前馈根本不触发） |
| `motor ff <c>` / `motor ff <1\|2> <c>` | 在线改前馈系数（同时改两轮 / 只改一路，0 < c ≤ 100；不清 PID 状态）。左轮系数 = 左轮落地挣脱点 × 1.1 ÷ 遥控目标，测法见[遥控速度的整定](#遥控速度的整定) |
| `motor stop` / `motor status` | 立即停 / 看两个电机的目标、实测、占空比、积分、当前增益、前馈系数 |
| `motor pid <kp> <ki> <kd>` | 在线改速度 PID 增益（两个电机同时换，并清 PID 状态；不用重新编译） |
| `follow status` | 跟随状态：状态词 / 点数和段数 / 当前段 / 已走里程 / 两轮累计计数。**同时在无线串口上可达**（`#follow status`），整定和排查都靠它 |
| `follow start [stop\|cont]` / `stop` | 开始 / 停止跟随（`stop` = 分段停走，默认；`cont` = 连续，转弯不停） |
| `follow begin <n>` / `wp <x> <y> <h>` / `end` | 手工灌一条路径（调试用；正常走上位机下发，见「航点跟随」一节） |
| `follow sign\|tol\|kp\|lead\|spd\|margin\|vmin\|vmax <值>` | 跟随的整定旋钮：符号 / 到位容差 / 转向 P / 提前刹车时间 / 巡航速度 / 提前停距 / 原地转最低最高速 |
| `jy901s` / `jy901s zero` | IMU 收字节数、有效帧数与角度，另外打印 RX 中断计数、解析线程唤醒次数和 P3_13 / LPUART3 的只读寄存器快照（自检用）/ 把当前朝向重新记为 0 度 |
| `oled screen car\|angle` | 切屏 |
| `oled test` / `clear` / `resume` | I2C 通路测试图案 / 清屏 / 恢复自动刷新 |
| `led` | 板载 RGB LED 手动控制 |

## 编译说明

### 依赖准备

BSP 依赖两个 packages（`nxp-mcx-cmsis-latest`、`nxp-mcx-series-latest`）。首次克隆或 packages
有更新时，先在 RT-Thread Env 中执行：

```bash
pkgs --update
```

`SConstruct` 里注册了 `bsp_pkg_check`，packages 缺失时会直接报错退出。

### GCC（命令行）

在 RT-Thread Env 中直接构建：

```bash
scons -j8
```

若不在 Env 环境中（例如从普通终端或 VSCode 任务调用），需手动提供两个环境变量：

```bat
set RTT_ROOT=D:\path\to\rt-thread
set RTT_EXEC_PATH=D:\path\to\env-windows\tools\gnu_gcc\arm_gcc\mingw\bin
D:\path\to\env-windows\.venv\Scripts\scons.exe -j8
```

`rtconfig.py` 的 `POST_ACTION` 会依次生成：

- `rtthread.elf` —— 调试用，含符号表
- `rtthread.bin` —— 纯二进制镜像
- `rtthread.hex` —— Intel HEX

清理：`scons -c`

### Keil MDK

双击打开 `project.uvprojx`，Target 为 `rtthread-frdm-mcxa346`，器件为 `MCXA346VLQ`。

也可以在 VSCode 中通过 Keil Assistant 插件构建（需先在插件设置中配置 Keil 安装路径）。

### 注意：两套工具链共用 `build/` 目录

Keil 工程的 `OutputDirectory` 配的是 `.\build\`，与 scons 的产物目录 **是同一个**。两者交替构建
时会混在同一目录下，排查问题时留意产物来源，避免误烧旧固件。

> `rtconfig.py` 的 `POST_ACTION` 特意补上了生成 `rtthread.hex` 这一步：否则 GCC 构建会留下上一次
> Keil 构建的旧 `rtthread.hex`，而 `mkdist.py` 并不排除 `*.hex`，容易烧错固件。

## VSCode 一键调试流程

本 BSP 在 VSCode 中按 F5 即可完成「构建 → 烧写 → 停在 main」。

### 前置条件

- 扩展 `marus25.cortex-debug`
- 板载 MCU-Link 已安装驱动（`D:/NXP/MCU-LINK_installer_2.263`）
- 已安装 LinkServer

### F5 的执行链路

```
F5
 └─ preLaunchTask: "debug-server"                    (launch.json)
     ├─ dependsOn: "build"                           → scons -j8 构建
     └─ .vscode/prepare-debug.ps1
         ├─ 回收上一次遗留的 gdbserver
         ├─ 等端口真正释放
         ├─ 启动 LinkServer gdbserver（监听 localhost:34443）
         └─ 阻塞到端口确实在监听才退出
 └─ cortex-debug 连接 34443，下载 rtthread.elf，运行到 main
```

### 四个文件的职责

| 文件 | 职责 |
| ---- | ---- |
| `.vscode/tasks.json` | 定义 `build` 与 `debug-server` 两个任务，后者通过 `dependsOn: ["build"]` 保证先构建 |
| `.vscode/prepare-debug.ps1` | `debug-server` 实际执行的内容：回收残留 gdbserver → 等端口释放 → 启动 LinkServer → **阻塞到端口真正监听**才退出 |
| `.vscode/launch.json` | 定义 cortex-debug 调试配置，`servertype` 为 `external`，通过 `gdbTarget` 连接 `localhost:34443` |
| `.vscode/settings.json` | 把 `debug.onTaskErrors` 设为 `abort`，脚本失败时直接取消调试会话，不再弹出「是否仍然继续」 |

> **关键点**：cortex-debug 的 `servertype: "external"` 语义是「外部的、已被启动的」server，
> 它**只负责连接，不会启动任何 server**。因此必须由 `debug-server` 任务先行拉起 LinkServer，
> 否则就会报 `Connection timed out`。

> **为什么用脚本而不是后台任务**：早期版本把该任务写成 `isBackground`，靠 problemMatcher 的
> `endsPattern`（匹配 `GDB server listening on port`）判断就绪。但一旦 LinkServer 启动失败
> （例如端口被占），那一行永远不会打印，VSCode 便不会显示 LinkServer 的真实错误，而是让
> cortex-debug 去连一个空端口，**30 秒后**才报 `Connection timed out` —— 看起来像是代码没编译过。
> 改成「脚本阻塞到监听成功才返回」后这个缝隙就没了：脚本以非零码退出时，VSCode 会**立即**
> 中止启动并显示脚本的错误信息（见「已解决问题记录」第 4 条）。

这两个文件**不在版本控制内**（仓库根 `.gitignore` 忽略了 `.vscode/`），完整内容见
[附录](#附录vscode-配置全文)，可直接复制还原。

### 已知限制

- 本机两个工具链的 `arm-none-eabi-gdb` **均不带 Python 支持**（`Python scripting is not
  supported in this copy of GDB`），因此 `prepare-debug.ps1` 里加了 `--no-rtos`，**RTOS 线程
  视图与外设寄存器视图不可用**；断点、单步、变量查看等基本功能正常。
- BSP 内没有 MCXA346 的 SVD 文件，且本机 Keil 只装了 pack 的在线索引（`PACK/.Web/`）而未
  实际安装，故外设寄存器面板暂不可用。
- `prepare-debug.ps1` 用 `--semihost-port -1` **显式关闭了 telnet semihosting**。本 BSP 的
  控制台走 uart2，不依赖它，关掉后 gdbserver 只占一个端口（否则还要额外占用 gdb 端口 +1）。
  若确实需要 telnet semihosting，去掉该参数即可，但端口冲突的概率会相应上升。

| 硬件定时器 | **已启用** | `BSP_USING_CLOCK_TIMER` + `BSP_USING_CTIMER0` |
| I2C | **已启用** | `BSP_USING_I2C` + `BSP_USING_I2C2`（LPI2C2 → 设备 `i2c2`，接 OLED） |
| PWM | **已启用** | `BSP_USING_PWM` + `PWM1` / `PWM2` + `BSP_PWM_FINE_PRESCALE`（电机调速） |
| SPI | 未启用 | `BSP_USING_SPI` 为 `not set` |
| ADC | 未启用 | `BSP_USING_ADC` 为 `not set` |
| RTC | 未启用 | `BSP_USING_RTC` 为 `not set` |
| WDT | 未启用 | `BSP_USING_WDT` 为 `not set` |
| CAN | 未启用 | `BSP_USING_CAN` 为 `not set` |
| DMA | 未启用 | `BSP_USING_DMA` 为 `not set` |
| CTIMER1 / 3 / 4 | 未启用 | 仅 CTIMER0 启用 |
| I2C3 | 未启用 | mikroBUS 座上的那路，当前没用到 |
| RTduino | 未启用 | `BSP_USING_ARDUINO` 为 `not set` |
| RW007 | 未启用 | `BSP_USING_RW007` 为 `not set` |

关于 LPUART5（无线串口模块用的那路）：

- `drv_uart.c` 原本只实现了 LPUART0~3，LPUART5 是本次移植新加的，**只加了 346/366 需要的
  部分**（`BSP_USING_UART5` 这个宏只定义在 `frdm-mcxa346/board/Kconfig`，其余三个 BSP
  不可能打开它）。
- **LPUART5\_TXD 在本板上换了焊盘，收发现在都用上了**：TXD 在这颗芯片上引到两个脚 ——
  P3_10 / Arduino D13 和 P1_10 / Arduino J2 第 3 脚。P3_10 被电机 2 的调速 PWM
  （FLEXPWM0\_A2）占用，而且 FLEXPWM0\_A2 **没有第二个焊盘**，换不动，所以走 P1_10。
  它在整个 BSP 里原本零引用（CAN0\_TXD 也复用在 P1_10，但本 BSP 没开 CAN），等于白空着。
  这一路现在跑编码器速度上报，见「无线串口命令表」的回程两节。
- LPUART5 的时钟门/分频寄存器区和 LPUART0~3 不同（`kCLOCK_GateLPUART5` 是
  `(0x10 << 16) | 22` 这种非典型编码），`drv_uart.c` 用的 `CLOCK_EnableClock()` 按寄存器
  偏移寻址，能正确处理，所以初始化路径和其它 UART 完全一样。

> **⚠️ 常见误区**：`RT_USING_I2C` / `RT_USING_SPI` / `RT_USING_ADC` / `RT_USING_RTC` 这些
> **框架层**宏是启用的，容易让人以为外设可用。但只有对应的 `BSP_USING_*` **驱动层**宏也打开，
> 固件里才会注册设备实例；否则 `rt_device_find("i2c3")` 之类会返回 `NULL`。
> 比如现在 I2C 框架开着、`BSP_USING_I2C2` 也开着，所以 `i2c2` 能用，但 `i2c3` 不行。
>
> 要启用某个外设，执行 `menuconfig`，在 `Onboard Peripheral Drivers` 下打开对应选项，
> 保存后重新编译。

## 已解决问题记录

以下问题在实际开发中遇到并已解决，记录以备查。第 1~5 条是配置 GCC + VSCode 开发环境时
踩到的工具链问题，第 6~7 条是给这块板子移植外设（OLED / IMU / 电机 / 无线串口）时踩到的
硬件与共享驱动问题。

### 1. IntelliSense 找不到 `stdint.h` / `stddef.h` / `time.h`

**现象**：VSCode 中打开 `components/libc/compilers/common/extension/sys/types.h`，第 15-17 行的
三个 include 全部标红报「找不到源文件」。

**根因**：`.vscode/c_cpp_properties.json` 是 `scons --target=vsc` 为 **armcc/Keil** 生成的旧模板，
从未随工具链切换更新：

- 没有 `compilerPath` 字段。正常配了它，扩展会直接向编译器查询内置头文件路径，无需手工维护；
- `includePath` 里全是 RT-Thread 自己的源码目录，**没有任何工具链目录**。

而这三个头文件都不是 RT-Thread 的，由工具链提供：

| 头文件 | 来源 | 路径 |
| ------ | ---- | ---- |
| `stdint.h`、`time.h` | newlib | `arm-none-eabi/include/` |
| `stddef.h` | GCC 内置 | `lib/gcc/arm-none-eabi/10.3.1/include/` |

`sys/types.h` 中的这三个 include 是**无条件**展开的，所以路径一断，三个同时报错。

**修复**：

1. 加 `compilerPath` 指向 `arm-none-eabi-gcc.exe`；
2. `intelliSenseMode` 从 `${default}` 改为 `windows-gcc-arm`；
3. 显式补上上述两个工具链 include 目录；
4. **删除 defines 里那批 armcc 兼容宏**（`__attribute__(x)=`、`__GNUC__=4`、`__declspec(x)=`
   等约 50 条）。它们是给 Keil 模拟 GCC 语法用的，配到真正的 GCC 上反而会把 `__attribute__`
   抹成空、把 `__GNUC__` 锁死在 4，制造大量假报错；
5. 删除与当前配置不符的 `RT_USING_LIBC` / `RT_USING_ARMLIBC`（`rtconfig.h` 中均未定义）。

改完需在 VSCode 中执行 `Developer: Reload Window` 才会生效。

### 2. F5 弹窗 `program '请输入程序名称，例如 ...\a.exe' does not exist`

**现象**：按 F5 后弹出错误框，程序路径是未替换的中文占位符。

**根因**：工程当时没有 `launch.json`，VSCode 找不到调试配置，便套用了 C/C++ 扩展的默认 cppdbg
模板，`program` 字段保持模板里的占位文本。且该模板面向**本机可执行文件**，对 Cortex-M33
固件并不适用，必须改用 cortex-debug。

**修复**：新建 `.vscode/launch.json`，使用 cortex-debug 配置（见附录）。

### 3. `Failed to launch GDB: localhost:3333: Connection timed out`

**现象**：F5 后 GDB 启动，但连接 `localhost:3333` 超时。

**根因**：cortex-debug 的 `servertype: "external"` 语义是「**externally controlled**」——
它**只负责连接，不会启动 server**。所以 3333 端口上根本没有东西在监听。

**为什么不用内置的 servertype**：cortex-debug 1.12.1 支持的取值只有
`jlink / openocd / pyocd / pe / stlink / stutil / qemu / bmp / external`，**没有 linkserver**。
而其余几条路在本机都不可行：

- J-Link、OpenOCD：未安装；
- pyOCD：装的是 0.45.1，内置 208 个 target，**整个 MCXA 系列一个都没有**。

LinkServer 是 NXP 官方调试服务，原生认识 `MCXA346:FRDM-MCXA346`，因此用它。

**修复**：在 `tasks.json` 中定义 `debug-server` 任务（普通任务，`dependsOn: ["build"]`）来启动
LinkServer，并让 `launch.json` 的 `preLaunchTask` 指向它，由它执行 `.vscode/prepare-debug.ps1`。
脚本阻塞到端口确实在监听之后才退出，因此 VSCode 启动 cortex-debug 时 server 一定已就绪。

两个细节：

- LinkServer 打印 `GDB server listening on port` 这行时走的是 **stdout**（`INFO:` 前缀的日志走
  stderr）；早期版本正是用这一行做就绪判断；
- 脚本保留了 `--update-mode none`，跳过 MCU-Link 固件更新检查。本机探针固件为 3.155，
  LinkServer 内置 3.172，检查只会产生提示。需要更新时手动执行
  `LinkServer probe #1 update auto`。

补充：LinkServer 在 GDB 断开连接后会**自行退出**，但这**不等于**重复按 F5 不会遇到端口占用 ——
退出并非瞬时完成，紧接着再按 F5 就会撞上自己上一次的残留。详见下面第 4 条。

### 4. `NoFreePortError: No available port in range 3333:3334`

**现象**：按 F5 后弹窗 `Failed to launch GDB: localhost:3333: Connection timed out`，而
`debug-server` 任务的终端里能看到 LinkServer 的真实报错：

```
CRITICAL: Critical error
ERRMSG: launcher.core.net.NoFreePortError: No available port in range 3333:3334 for host 127.0.0.1
```

**根因**：这条报错**与编译无关**，是 gdbserver 根本没起来。

`LinkServer.exe gdbserver --help` 显示，它除 `--gdb-port` 外还有一个 `--semihost-port`
（默认取 `gdb-port + 1`）。也就是说 gdbserver **要独占一对端口**，报错里的 `range 3333:3334`
正是这一对。由此有两个后果：

1. **3333 或 3334 任意一个被占，gdbserver 就整体启动失败**，冲突面比预想的翻倍；
2. 停止上一次调试后 LinkServer 才释放这对端口，且**释放有延迟**。此刻立刻再按 F5，就会撞上
   自己上一次的残留 —— 这正是「有时候能烧进去有时候烧不进去」的由来。

而这套失败在旧配置下会被**放大成误导**：LinkServer 秒退 → `endsPattern`
（`GDB server listening on port`）永远不匹配 → VSCode 不显示 LinkServer 的报错，转而让
cortex-debug 去连一个空端口 → 30 秒后才抛 `Connection timed out`。看起来像是代码没编译过，
而实际编译完全正常。

**修复**：三处一起改（详见「VSCode 一键调试流程」一节）：

- 把 `gdbserver` 从**后台任务**改为执行 `prepare-debug.ps1` 的**普通任务**，不再用
  `endsPattern` 猜测就绪，消除上面那条误导链；
- 脚本启动前先回收遗留的 gdbserver，并轮询等待端口释放，消除「停止后立刻再按 F5」的竞态；
- 改用 34443 并加 `--semihost-port -1`，让 gdbserver 只占一个端口，避开 3333/3334 这对
  高频占用端口。

**排查手法**：今后若再遇到，先查端口被谁占着 ——

```bash
netstat -ano | grep -E ":34443 "        # 最后一列是 PID
tasklist /FI "PID eq <PID>"             # 再看这个 PID 是什么程序
```

若占用者是遗留的 `LinkServer.exe gdbserver`，结束它即可；若是其它程序，则修改
`prepare-debug.ps1` 里的 `$GdbPort`，并同步修改 `launch.json` 的 `gdbTarget`。

### 5. 探针未连接，也会表现为 `Connection timed out`

**现象**：与第 4 条**一模一样**的弹窗 `Failed to launch GDB: ... Connection timed out`，
但 `debug-server` 任务的终端（以及 `.vscode/gdbserver.log.err`）里写的是：

```
INFO: Selected device MCXA346:FRDM-MCXA346
CRITICAL: Critical error
ERRMSG: Exception: No probes detected
```

**根因**：板子没插，或 USB 掉了。

`Connection timed out` 只是**表症** —— 凡是 LinkServer 没起来的原因，最后都以这句呈现。
所以看到它，**先去看任务终端或 `.vscode/gdbserver.log.err`**，那里才是真正的原因。

**排查手法**：

```bash
LinkServer probes        # 探针表为空 = 没插上
```

也可在设备管理器里看：MCU-Link 不在位时，相关设备会以 `Unknown` 状态留在驱动库中
（历史上装过驱动），但不出现在当前设备列表里。

**缓解**：`.vscode/settings.json` 中的 `debug.onTaskErrors: "abort"` 正是为此 —— 脚本失败时
VSCode 直接取消调试会话，而不是弹出「是否仍然继续」，免得点进去再白等 30 秒超时。

### 6. 想给无线串口模块加串口，选好的引脚在未贴装的排针上

**现象**：给无线串口模块挑串口时，第一选是 **P4_4 / LPUART4\_RXD**（芯片手册上确实有这个复用），
但这一脚在本板上接不出来。

**根因**：P4_4 引到的 **J8** 是 **DNP（Do Not Populate，未贴装）**。FRDM-MCXA346 没焊 J8 和 J19
这两排排针 —— 因为 MCXA346 **没有 FlexIO 模块**，NXP 干脆把它们省掉了。所以凡是只出现在
J8/J19 上的引脚，在这块板子上都拿不到。

**修复**：改用 **P3_11 / Arduino D10 / LPUART5\_RXD（ALT8）**，在 Arduino 排针上，插上就能用。

**顺带一个坑**：`pin_mux.c` 原本**无条件**把 P3_11 配成 mikroBUS 的 **LPSPI1\_PCS0（ALT2）**，
会盖掉 ALT8。所以这一块必须加守卫，让 `BSP_USING_UART5` 打开时走 UART 分支。同一文件里的
P3_8 / P3_10 早就有同样的 `#ifndef BSP_USING_PWM` 守卫（电机调速也踩过这个坑）。

**同一课的第二遍（加编码器速度上报的回程 TX 时）**：原以为无线串口模块这条链路注定只能收 ——
芯片手册上 LPUART5\_TXD 看着只有 **P3_10 / Arduino D13** 一个焊盘，而 D13 被电机 2 的调速
PWM 占着。但**同一个复用功能经常有不止一个焊盘**：翻 SDK 的板级 `pin_mux.c`（lpadc 例程的
注释直接写着 `J2-3(P1_10)`）才看到 LPUART5\_TXD 还能走 **P1_10 / Arduino J2 第 3 脚**，
也在已贴装的排针上，正好够回程用。所以查一个复用功能时要把它的**所有**焊盘都列出来再挑，
不是挑到第一个被占就放弃。（反过来也成立：`FLEXPWM0_A2` 就**只有** P3_10 这一个焊盘，
电机 PWM 那边才是真的换不动，只能让串口换到 P1_10。）

**教训**：在这块板子上选引脚，**先确认它在 Arduino 排针或 mikroBUS 座上**，再看芯片有没有
那个复用功能。反过来（先看手册再找焊盘）会挑到 J8/J19 上拿不到的脚。芯片手册的复用表
不会告诉你哪一脚在板上是 DNP —— 要看 UM12348 的排针表和 `pin_mux.c` 里实际配了哪些脚。
还有一条：**别从 SDK `pin_signal` 字符串的排位去推 ALT 值**，两者没有对应关系 —— 本 BSP 里
P1_11 的 CAN0\_RXD 排第 8 位却是 ALT11，P3_11 的 LPSPI1\_PCS0 排第 3 位却是 ALT2，
P1_10 的 ADC1\_A8 排在最后却是 ALT0。要 ALT 编号只能查 RM 的复用表（同一复用功能的所有脚
共用一个 ALT 值：LPUART5 全家是 ALT8，CAN0 全家是 ALT11），或者照抄 SDK 例程里写好的
`kPORT_MuxAltN`。

### 7. 给共享驱动加 UART 通道，注意别影响同系列其它 BSP

**现象**：`libraries/drivers/drv_uart.c` 是 mcxa153/156/346/366 **四个 BSP 共享**的，
而 LPUART5 只有 346/366 才有。改错了会让另外两个型号编译不过。

**处理**：新增的代码整段包在 `#if defined(BSP_USING_UART5)` 里，而 `BSP_USING_UART5` 这个宏
**只定义在 `frdm-mcxa346/board/Kconfig`**（其余 BSP 连 `packages/` 都没拉，本来也编译不了）。
所以新增代码对其它 BSP 不可达，不会改变它们的任何行为。如果以后要在 **366** 上开这一路，
直接加上同名 Kconfig 选项即可 —— 用到的 `kCLOCK_GateLPUART5` / `kFRO_LF_DIV_to_LPUART5`
宏在 346 和 366 的 SDK 头文件里都有。

## 已知问题（未验证）

以下问题都是在阅读源码时发现的，**尚未在硬件上实际触发验证**，仅供参考。
第 1、2 条是配置层面的不一致，第 3~8 条是无线串口遥控移植完成后复查代码查出来的。

> 已修掉、不再属于本节的：换向时不卸力、弧线转弯内侧速度低于起动转速、`bt link` 参数溢出、
> `jy901s.c` 的串口配置被 `-RT_EBUSY` 静默丢弃 —— 四个都已改为正确实现。


1. **`board/SConscript` 的 RW007 路径可能不存在**

   第 12-13 行在 `BSP_USING_RW007` 时会 `Glob('ports/drv_spi_sample_rw007.c')`，但 `board/ports/`
   目录并不存在。实际的示例文件位于 `applications/drv_spi_sample_rw007.c`，而它会被
   `applications/SConscript` 的 `Glob('*.c')` 无条件编译。开启 RW007 时可能因此报错。

2. **`board/Kconfig` 中部分 `select` 目标符号未定义**

   `Onboard Peripheral Drivers` 里 `select` 的 `BSP_USING_GPIO`、`BSP_USING_ADC0`、
   `BSP_USING_PWM0/1`、`BSP_USING_I2C1/2` 等符号在 Kconfig 中并未定义（真实符号是
   `BSP_USING_PIN`、`BSP_USING_ADC0_CH22`、`BSP_USING_I2C3` 等）。RTduino 选项的 `select`
   目标与真实符号不匹配，可能不会按预期打开对应驱动。

3. **上电那张命令表只闪几毫秒**

   见上面「两块屏幕」一节的说明：`angle_display_init()` 画完 `DrawBootScreen()` 就起了显示线程，
   线程第一轮发现屏幕编号从 `0xFF` 变成了实际值，于是清屏重画。想让它停留一会儿得在线程里
   加一段宽限期，本次没加（理由见那节）。

4. **`bt lock` / `bt unlock` 与遥控线程并发**

   [bt_car.c:445](applications/bt_car.c#L445) 的 msh 分支直接从 tshell 线程调 `bt_apply()`，
   而同一个函数也被遥控线程调用（[bt_car.c:213](applications/bt_car.c#L213)）。
   tshell 优先级 20 高于遥控线程 23，所以遥控线程可能在 `bt_apply()` **中间**被抢占。

   单个变量不会撕裂（`g_armed` 是 8 位、`g_state` 是 32 位枚举，都是单指令访问），
   但一次动作要写两个轮子的目标，这两次 `motor_set_target()` 之间没有保护。交错的结果是
   **两轮目标来自两条不同的命令**：例如 tshell 的 `bt unlock` 已经写了左轮、遥控线程的 `A`
   插进来写了左轮+右轮，最终左轮是自转值、右轮是解锁时的刹车值 —— 车会以一个谁也没下过的
   组合走，**而且这个组合会一直保持到下一条命令到达**（PID 只负责跟着目标走，不会"纠正"回
   某条命令）。这是本节里唯一有实际运动风险的条目。

   只在 msh 和上位机**同时**发命令时才会碰上（人手敲命令的速率很低），所以本次没加锁。
   但如果以后要做「msh 遥控 + 上位机遥控」混用，必须先给 `bt_apply()` 加互斥锁。

5. **`oled test` / `oled clear` 是 OLED 的第二个写入者**

   [angle_display.c:541-555](applications/angle_display.c#L541-L555)：这两个分支先置
   `display_paused = RT_TRUE`、紧接着就在 tshell 线程里画。而显示线程只在每轮循环
   **开头**检查 `display_paused`（[angle_display.c:353](applications/angle_display.c#L353)），
   所以如果它此刻正卡在 `OLED_Refresh()`（[oled.c:88-112](applications/oled.c#L88-L112)，
   一次刷屏 = 8 页 × 2 = **16 次 I2C 传输**）中间，tshell（优先级 20）一抢占就把
   自己那 16 次传输插进去 —— SSD1306 收到的是两帧交错的数据，屏幕上出现花屏。
   概率低（刷新窗口很短）且**再执行一次 `oled clear` 就能清掉**，所以没为它加锁。
   注意 `oled screen` 那条分支是刻意不画的（见那里的注释），不受这条影响。

6. **`JY61P_HasNewData()` / `JY61P_ClearNewData()` 是"先查后清"**

   [angle_display.c:359-365](applications/angle_display.c#L359-L365) 先问有没有新数据、
   再读 `jy61p` 快照、最后清标志。解析线程优先级 22 高于显示线程 26，如果在这一小段里
   恰好又来了一帧，被清掉的是**后到那一帧**的标志，于是显示层少画一帧
   （丢掉的那一帧的解算结果仍然被写进了 `jy61p`，会被下一轮读到）。
   表现为角度屏偶尔少刷新一次，不丢数据、不影响闭环。改成"原子取走"需要给
   `jy61p` 加锁或双缓冲，本次没做。

7. **`yaw_boot_cnt` 少了 `volatile`**

   [jy901s.c:55](applications/jy901s.c#L55) 的 `static uint8_t yaw_boot_cnt` 被两个线程写：
   解析线程（[jy901s.c:186-187](applications/jy901s.c#L186-L187)）和 `JY61P_ZeroYaw()`
   （[jy901s.c:134](applications/jy901s.c#L134)，由 msh 的 `jy901s zero` 从 tshell 线程调用），
   但没像隔壁的 `yaw_zeroed` 那样加 `volatile`。开了 `-O` 之后编译器有权把它缓存在寄存器里，
   于是 tshell 里的清零可能不被解析线程看到。

   具体后果（不是"零点失效"）：重新对零时 `JY61P_ZERO_SKIP`（[jy901s.c:78](applications/jy901s.c#L78)，
   值 5）那 5 帧的"等模块稳下来"窗口被跳过，新零点直接在命令后的第一帧上锁定。
   因为 `yaw_zeroed` 是 `volatile`、清零一定看得见（[jy901s.c:185](applications/jy901s.c#L185)），
   所以**重新对零本身一定成功**，最坏情况只是零点取自一帧还没稳的数据 ——
   而此时模块已经连续输出很久，帧本身就是稳的，实践中看不出来。
   同时这个窗口只在"上电头几帧"才有意义，所以影响面很窄。
   本次未改（`volatile` 只保证可见性、不保证原子性，真要修应该连 `yaw_zeroed` 一起看）。

8. **两处不可达的移植缺陷**

   `applications/oled.c` 是从上游照搬的库，里面有两个 bug，但**都没有调用者**
   （已在 `rtthread.elf` 里确认被链接器回收，`nm` 查不到符号）：

   - `OLED_DisPlay_Off()`（[oled.c:84](applications/oled.c#L84)）写的是 `0xAF`，注释却写"关闭屏幕"。
     `0xAF` 是**点亮**（`0xAE` 才是关闭），所以调它不会关屏。本工程用的是软件关屏
     （`OLED_ColorTurn` / 直接清屏），不依赖这个函数。
   - `OLED_DrawCircle(x, y, 0)`（[oled.c:173-191](applications/oled.c#L173-L191)）会**死循环**：
     `r = 0` 时循环条件 `2*b*b >= r*r` 恒为 `0 >= 0` 成立，而 `b--` 每轮把 `b` 压到更负，
     条件永远不假。画圆半径传 0 就会卡死在 tshell 线程里。

   两处都**没改**：按仓库规则（`AGENTS.md`）不应擅自修改导入的第三方代码，
   而本工程没有任何代码路径会调到它们。如果要给这两个函数接调用者，先修掉这两处。

### `.vscode/prepare-debug.ps1`

> 这个文件**必须以 UTF-8 with BOM 保存**。Windows PowerShell 5.1 读取无 BOM 的 `.ps1` 时
> 会按系统 ANSI 码页解码，脚本里的中文注释会被读成乱码并直接导致语法解析失败
> （`ParserError: UnexpectedToken`）。

```powershell
# 为 cortex-debug 准备 LinkServer gdbserver。
#
# 这是 launch.json 的 preLaunchTask("debug-server") 实际执行的脚本。它是一个**普通任务**
# 而非后台任务：脚本一直阻塞到 server 真正监听成功才返回，所以 VSCode 一等到脚本退出，
# 端口上就一定有东西在等 cortex-debug —— 不需要 problemMatcher/endsPattern 那套猜测。
#
# 解决的故障：LinkServer 的 gdbserver 需要独占 gdb 端口和 semihost 端口（默认 gdb+1）。
# 任意一个被占，它就抛 NoFreePortError 秒退；而 cortex-debug 只会看到「连不上」，
# 于是 30 秒后报 Connection timed out，把人误导成「代码没编译过」。
#
# 手工运行：
#   powershell -NoProfile -ExecutionPolicy Bypass -File .vscode/prepare-debug.ps1

$ErrorActionPreference = 'Stop'

$Root       = Split-Path -Parent $PSScriptRoot          # 脚本在 .vscode/ 下，上一级即 BSP 根目录
$LinkServer = 'C:\NXP\LinkServer_26.6.137\LinkServer.exe'
$Device     = 'MCXA346:FRDM-MCXA346'
$GdbPort    = 34443
# 换端口的话，launch.json 里的 gdbTarget 必须同步改。
$LogFile    = Join-Path $PSScriptRoot 'gdbserver.log'

function Test-PortListening([int]$Port) {
    [bool](Get-NetTCPConnection -LocalPort $Port -State Listen -ErrorAction SilentlyContinue)
}

# 1) 回收上一次遗留的 gdbserver。
#    停止调试后 LinkServer 确实会自行退出，但**不是瞬间**的；此时立刻再按 F5 就会撞上
#    上一次的残留。按命令行过滤而非按进程名，避免误伤 LinkServer 的其它用途。
Get-CimInstance Win32_Process -Filter "Name='LinkServer.exe'" |
    Where-Object { $_.CommandLine -like '*gdbserver*' } |
    ForEach-Object {
        Write-Host "清理遗留 gdbserver: PID $($_.ProcessId)"
        Stop-Process -Id $_.ProcessId -Force -ErrorAction SilentlyContinue
    }

# 2) 等端口真正释放——专治「停止后立刻再按 F5」的竞态。
#    只在占用者是 LinkServer（即刚被上面结束、正在退出）时才值得等；若是别的程序占着，
#    等多久都没用，直接落到第 3 步报错，不让用户白等 10 秒。
$deadline = (Get-Date).AddSeconds(10)
while ((Get-Date) -lt $deadline) {
    $c = @(Get-NetTCPConnection -LocalPort $GdbPort -State Listen -ErrorAction SilentlyContinue)[0]
    if (-not $c) { break }
    if ((Get-Process -Id $c.OwningProcess -ErrorAction SilentlyContinue).ProcessName -ne 'LinkServer') { break }
    Start-Sleep -Milliseconds 300
}

# 3) 仍被占用——立刻失败并指名道姓。
#    必须迅速退出：宁可让 VSCode 中止启动并显示下面这行，也不要拖到 GDB 超时。
$c = @(Get-NetTCPConnection -LocalPort $GdbPort -State Listen -ErrorAction SilentlyContinue)[0]
if ($c) {
    $pname = (Get-Process -Id $c.OwningProcess -ErrorAction SilentlyContinue).ProcessName
    Write-Error "端口 $GdbPort 被 PID $($c.OwningProcess) ($pname) 占用，且不是 LinkServer gdbserver。请释放该端口，或改用其它端口（需同步修改 launch.json 的 gdbTarget）。"
    exit 1
}

# 4) 拉起 gdbserver。
#    --semihost-port -1 关掉 telnet semihosting：本 BSP 控制台走 uart2，用不到它，
#    关掉后 server 只占一个端口，端口冲突的概率直接减半。
#    用 Start-Process 起成独立进程并把输出落盘：既留下日志便于排查，也避免任务终端
#    关闭时牵连子进程。
$lsArgs = @(
    'gdbserver',
    '--gdb-port', "$GdbPort",
    '--semihost-port', '-1',
    '--update-mode', 'none',
    '--no-rtos',
    $Device
)
Start-Process -FilePath $LinkServer -ArgumentList $lsArgs -WorkingDirectory $Root `
    -RedirectStandardOutput $LogFile -RedirectStandardError "$LogFile.err" `
    -WindowStyle Hidden -PassThru | Out-Null

# 5) 等监听就绪。
$deadline = (Get-Date).AddSeconds(20)
while (-not (Test-PortListening $GdbPort) -and (Get-Date) -lt $deadline) {
    Start-Sleep -Milliseconds 300
}

if (-not (Test-PortListening $GdbPort)) {
    Write-Host '---- gdbserver.log (tail) ----'
    Get-Content $LogFile, "$LogFile.err" -ErrorAction SilentlyContinue | Select-Object -Last 30
    Write-Error "LinkServer 未能在 20 秒内监听 $GdbPort（探针没插？被别的调试器占用？详见上面的日志尾部）。"
    exit 1
}

Write-Host "GDB server listening on port $GdbPort"
exit 0
```

调试失败时，LinkServer 的完整输出留在 `.vscode/gdbserver.log`（stdout）与
`.vscode/gdbserver.log.err`（stderr）中，脚本在超时时也会自动打印两者的尾部 30 行。
